# 职航智管：高校毕业生就业规划与求职事务智能体设计方案

## 1. 项目概述

### 1.1 项目名称

职航智管：高校毕业生就业规划与求职事务智能体

### 1.2 项目定位

面向高校应届毕业生和就业辅导员，建设“学生求职执行 + 辅导员就业管理”的双端智能系统。系统围绕毕业生求职全过程，将就业画像、职业规划、岗位匹配、简历优化、模拟面试、投递管理、求职复盘和辅导干预连接为持续运行的闭环。

本项目不是单一问答机器人。AI 负责理解、分析、规划和生成，业务系统负责记录任务、跟踪状态、呈现依据和支持人工干预。

### 1.3 赛道与场景

- 参赛方向：校园管理方向、AI Agent 应用。
- 真实场景：高校毕业生就业指导、求职过程管理和重点学生帮扶。
- 主要用户：应届毕业生、就业辅导员和学校就业管理人员。

### 1.4 核心问题

1. 学生缺少清晰的岗位目标和可执行的求职计划。
2. 简历、岗位、投递、面试和复盘信息分散，难以形成持续改进。
3. 辅导员面对大量学生，只能被动收集结果，难以及时发现求职停滞。
4. 现有通用大模型回答缺少学生上下文、过程记录和任务闭环。

### 1.5 项目目标

首版支持一名学生从上传简历开始，完成一次完整的“就业诊断、目标规划、岗位匹配、简历优化、模拟面试、投递记录和求职复盘”；同时，辅导员能够查看班级总体进度、学生风险依据和建议干预动作。

## 2. 用户角色与使用目标

### 2.1 学生端

学生希望明确适合的岗位，获得针对目标岗位的准备建议，并在一个地方持续管理求职任务、材料、投递和面试结果。

主要目标：

- 建立可确认、可更新的个人就业档案。
- 获得有依据的岗位方向和行动计划。
- 针对具体岗位优化简历并完成面试训练。
- 管理投递进度，定期复盘求职策略。
- 接收和完成辅导员布置的帮扶任务。

### 2.2 辅导员端

辅导员希望快速了解班级就业进展，定位真正需要帮助的学生，并通过有依据的方式进行分层干预。

主要目标：

- 查看班级求职阶段、任务完成率和投递漏斗。
- 查看风险学生、触发事实和近期变化。
- 按风险原因筛选学生并发起帮扶任务。
- 查看学生反馈和任务完成情况。
- 导出脱敏统计数据，用于就业工作复盘。

### 2.3 就业管理人员

首版仅提供聚合统计和规则配置能力，不单独建设复杂的校级管理后台。

## 3. 产品闭环

```text
学生建立就业档案
    ↓
AI 生成能力画像与求职目标
    ↓
拆解四周计划，辅助岗位匹配、简历优化和面试训练
    ↓
学生记录投递、笔试和面试结果
    ↓
AI 按周复盘并调整求职策略
    ↓
辅导员查看进度、风险依据和干预建议
    ↓
辅导员布置任务或提供帮扶
    ↓
结果返回学生端继续执行
```

## 4. 总体架构

### 4.1 多智能体架构

系统采用“1 个主智能体 + 6 个专业智能体 + 1 个规则引擎”。

```text
就业管家主智能体
├── 就业画像智能体
├── 职业规划智能体
├── 岗位匹配智能体
├── 简历优化智能体
├── 模拟面试智能体
├── 求职复盘智能体
└── 事务与风险规则引擎
```

| 模块 | 主要输入 | 主要输出 |
| --- | --- | --- |
| 就业管家主智能体 | 用户问题、学生档案、当前任务 | 意图识别、流程调度、综合答复 |
| 就业画像智能体 | 专业、技能、经历、简历、就业偏好 | 能力标签、优势证据、能力缺口、目标约束 |
| 职业规划智能体 | 就业画像、目标城市和行业 | 目标岗位组合、备选路径、四周行动计划 |
| 岗位匹配智能体 | 学生画像、岗位描述 | 匹配度、匹配依据、能力差距、投递建议 |
| 简历优化智能体 | 原简历、目标岗位 | 问题诊断、针对性修改、修改依据 |
| 模拟面试智能体 | 岗位要求、简历内容 | 个性化问题、动态追问、评分证据、训练建议 |
| 求职复盘智能体 | 投递、笔试、面试及结果记录 | 漏斗分析、问题假设、下一步策略 |
| 事务与风险规则引擎 | 活跃度、任务、投递和面试数据 | 风险等级、触发事实、干预建议 |

### 4.2 系统分层

1. 展示层：学生端和辅导员端 Web 应用。
2. 业务层：用户权限、档案、任务、岗位、投递、面试、干预和统计服务。
3. Agent 层：主智能体、专业智能体、工作流编排和结构化输出校验。
4. 知识层：岗位知识库、简历规则、面试题库、就业政策和学校办事指南。
5. 数据层：结构化业务数据、文件存储、审计记录和脱敏分析数据。

### 4.3 赛事工具分工

- 深信服 SF-FastGPT：承载主智能体、专业智能体、提示词、知识库检索和工作流编排。
- 超星 AI 能力中心：提供大模型和多模态能力。未取得账号前先接入兼容模型接口，取得权限后通过模型适配器切换。
- 百川云璟数据集平台：获取或维护脱敏岗位、简历样例、面试题和就业政策数据，用作知识库与测试集。
- 自建轻量业务系统：管理双端页面、身份权限、任务状态、投递记录和统计看板。

模型与平台通过统一适配接口接入，避免项目在赛事账号未开通时停滞。

### 4.4 技术路线选择

项目采用“Python 模块化单体 + React 双端 Web + SF-FastGPT 智能体编排”路线。该路线兼顾 AI 集成效率、业务完整性、比赛展示效果和部署复杂度。

| 技术路线 | 优点 | 局限 | 结论 |
| --- | --- | --- | --- |
| React + FastAPI + SF-FastGPT | AI 集成方便、开发速度快、部署简单 | 团队需要掌握 Python 与 TypeScript | 推荐采用 |
| React + Spring Boot + Python AI 服务 | 企业业务能力成熟，适合 Java 团队 | 服务和部署更复杂，首版工作量较大 | 团队以 Java 为主时备选 |
| SF-FastGPT + 低代码页面 | 原型制作最快 | 事务状态、细粒度权限和统计看板能力有限 | 仅用于概念验证 |

首版不拆分微服务。后端使用一个 FastAPI 应用，并通过内部业务模块保持边界清晰。取得赛事账号后，仅替换模型与 Agent 适配器，不重写前端和业务系统。

### 4.5 推荐技术栈

| 层级 | 技术或框架 | 主要用途 |
| --- | --- | --- |
| 前端基础 | React、TypeScript、Vite | 构建学生端和辅导员端单页应用 |
| UI 与样式 | Tailwind CSS、shadcn/ui | 构建表单、表格、看板和弹窗等业务界面 |
| 图标 | Lucide React | 提供统一的功能图标 |
| 页面路由 | React Router | 管理学生端、辅导员端页面和权限路由 |
| 请求状态 | TanStack Query | 管理接口请求、缓存、重试和页面状态同步 |
| 表单校验 | React Hook Form、Zod | 管理就业档案、岗位和任务表单校验 |
| 数据图表 | Apache ECharts | 展示投递漏斗、求职阶段和风险分布 |
| 后端基础 | Python、FastAPI | 提供业务接口、权限控制、Agent 调用和文件处理 |
| ORM | SQLAlchemy 2 | 访问关系型数据库 |
| 数据迁移 | Alembic | 管理数据库结构版本 |
| 数据校验 | Pydantic 2 | 校验接口数据和 Agent 结构化输出 |
| 关系数据库 | PostgreSQL | 保存用户、档案、任务、投递、风险和审计数据 |
| 文件存储 | MinIO | 保存简历和导出文件；演示阶段可先使用本地目录 |
| 定时任务 | APScheduler | 执行到期提醒、每日风险规则扫描和定期复盘 |
| Agent 编排 | SF-FastGPT | 承载主智能体、专业智能体、工作流和知识库 |
| 模型能力 | 超星 AI 或兼容模型接口 | 提供文本理解、生成和可用的多模态能力 |
| 数据集 | 百川云璟 | 获取脱敏岗位、简历、面试和政策数据 |
| 文档解析 | PyMuPDF、python-docx | 解析 PDF 和 DOCX 简历 |
| 网关与部署 | Nginx、Docker Compose | 统一入口并一键启动前端、后端、数据库和存储 |
| 自动化测试 | Pytest、Vitest、Playwright | 测试后端、前端组件和双端核心业务流程 |

依赖版本在开发计划阶段统一锁定，并通过依赖文件和容器镜像保证演示环境可复现。

### 4.6 后端模块划分

```text
backend/
├── auth             # 登录、JWT和角色权限
├── students         # 学生档案与就业画像
├── plans            # 求职目标和四周计划
├── jobs             # 岗位和匹配结果
├── resumes          # 简历文件与版本
├── interviews       # 模拟面试记录
├── applications     # 投递事务看板
├── risks            # 风险规则与风险事件
├── interventions    # 辅导员帮扶任务
├── agents           # FastGPT和模型适配接口
└── audit            # 操作与模型调用审计
```

模块化单体既能保持代码职责清晰，又只需部署一个后端服务，避免首版引入服务注册、消息队列和分布式事务。

### 4.7 AI 调用链

```text
React 页面
    ↓ REST API
FastAPI 业务服务
    ├── 读取学生档案、岗位和任务
    ├── 调用 Agent Gateway
    │       ├── SF-FastGPT
    │       └── 前期兼容模型接口
    ├── 使用 Pydantic 校验结构化输出
    ├── 等待学生或辅导员确认
    └── 将正式结果写入 PostgreSQL
```

Agent Gateway 是平台适配层。前期没有赛事账号时接入兼容模型；取得权限后切换至 SF-FastGPT 和超星 AI，双端页面、业务规则及数据结构保持不变。

SF-FastGPT 负责：

- 主智能体识别用户意图并调度专业智能体。
- 检索简历规范、面试题和就业政策知识库。
- 生成符合约定 JSON Schema 的结构化结果。
- 记录工作流节点和调试信息，支持比赛展示。

FastAPI 负责：

- 登录权限和学生数据隔离。
- 上传、解析和管理简历文件。
- 保存任务、投递、风险和干预状态。
- 执行确定性的风险规则。
- 校验模型结果并处理人工确认。
- 为辅导员看板提供聚合统计数据。

项目不同时引入 LangChain、Dify 等第二套 Agent 编排框架，避免重复编排、调试困难以及弱化 SF-FastGPT 在作品中的核心作用。

### 4.8 首版不采用的技术

首版不引入 Kubernetes、Kafka、微服务、独立向量数据库、模型微调、原生鸿蒙客户端和视频表情识别。知识库优先使用 SF-FastGPT，移动端通过响应式 Web 支持；确有安装入口需求时再增加 PWA 能力。

## 5. 学生端功能

### 5.1 就业工作台

首屏直接展示当前目标、求职阶段、今日任务、近期待办、投递漏斗和 AI 建议。避免将聊天框作为唯一入口。

### 5.2 就业档案与画像

- 填写专业、技能、项目、实习、证书、城市、行业、薪资和岗位偏好。
- 上传 PDF 或 DOCX 简历并抽取结构化信息。
- AI 抽取结果必须由学生确认后才写入正式档案。
- 每项能力标签显示来源证据，不凭空补全经历。

### 5.3 目标与四周计划

- 推荐 1 个主目标岗位和最多 2 个备选岗位。
- 说明推荐依据、能力差距和不确定因素。
- 将建议拆分为四周任务，任务包含截止日期、完成标准和关联材料。
- 学生可接受、修改或拒绝任务，不强制执行 AI 建议。

### 5.4 岗位匹配

- 支持粘贴岗位描述或从演示岗位库选择岗位。
- 从硬性条件、技能、经历、偏好和发展方向五个维度分析。
- 输出“适合投递、补充后投递、暂不建议”三级结论。
- 匹配结果必须引用简历和岗位描述中的原文证据。

### 5.5 简历优化

- 对目标岗位执行针对性诊断，不生成虚假经历。
- 采用原文、修改建议和修改理由对照展示。
- 对缺少量化结果的经历提出补充问题，由学生填写事实。
- 保存不同岗位对应的简历版本。

### 5.6 模拟面试

- 根据岗位描述和学生简历生成个性化问题。
- 根据学生回答进行动态追问。
- 从内容完整性、岗位相关性、表达结构和证据充分度评分。
- 输出事实型反馈，不依据口音、性别、外貌等特征评分。

### 5.7 求职事务管理

- 使用看板管理“待投递、已投递、笔试、面试、录用、结束”。
- 每条记录关联岗位、简历版本、时间、结果和下一步任务。
- 支持提醒笔试、面试、材料提交和结果跟进。

### 5.8 每周复盘

- 统计新增岗位、投递、回复、笔试、面试和录用数量。
- 结合数据提出最多 3 条优先改进建议。
- 学生确认后更新下一周计划。

## 6. 辅导员端功能

### 6.1 班级就业驾驶舱

展示班级学生数、活跃学生数、已建立目标数、近七日投递数、进入面试数、获得录用数和需关注学生数。

### 6.2 学生分层列表

按求职阶段、任务状态和风险原因筛选。风险分为正常、关注和需干预三级，每条风险都显示触发事实与更新时间。

### 6.3 学生详情

查看学生目标岗位、计划完成情况、求职漏斗、近期活动、AI 建议和历史干预记录。默认不展示不必要的个人敏感信息。

### 6.4 帮扶任务

- 向单个或一组学生布置简历完善、岗位投递、面谈预约等任务。
- 学生可反馈完成结果或说明困难。
- 辅导员可以确认完成、补充建议或转为线下帮扶。

### 6.5 汇总与导出

输出班级维度的求职阶段、投递漏斗、风险原因分布和任务完成率。导出内容默认脱敏，并记录导出操作。

## 7. 风险识别与人工干预

风险判断以可解释规则为主，大模型仅负责归纳和建议。

首版规则示例：

| 风险事实 | 建议等级 | 建议动作 |
| --- | --- | --- |
| 建档后 7 天未确定目标岗位 | 关注 | 邀请完成目标澄清任务 |
| 连续 14 天无投递记录 | 需干预 | 了解阻碍并布置一次岗位筛选 |
| 四周计划逾期 3 项及以上 | 关注 | 调整任务粒度和截止时间 |
| 投递 20 次但无笔试或面试 | 需干预 | 检查岗位匹配和简历质量 |
| 连续 3 次面试未通过 | 需干预 | 安排模拟面试或人工辅导 |

限制要求：

- 不使用性别、民族、家庭情况等敏感属性计算风险。
- 不预测学生能否就业，不自动形成处分或资源限制。
- 辅导员必须能查看规则、事实依据并人工确认。
- 学生可对错误记录提出更正。

## 8. 核心数据设计

首版只保留支撑闭环所需的数据实体：

- 用户：身份、角色、班级和权限。
- 学生档案：专业、技能、经历、偏好及确认状态。
- 求职目标：主目标、备选目标、城市和行业。
- 任务：类型、截止日期、完成标准、状态和来源。
- 岗位：岗位描述、企业、地点和结构化要求。
- 简历版本：原文件、目标岗位、修改记录和确认状态。
- 投递记录：求职阶段、关键时间、结果和关联简历。
- 面试记录：问题、回答、反馈和学生确认。
- 风险事件：规则、触发事实、等级、状态和处理结果。
- 干预记录：发起人、任务、反馈、处理结果和时间。
- 审计日志：模型调用、数据变更、导出和人工确认记录。

## 9. Agent 工作流与输出约束

### 9.1 调度原则

主智能体先识别意图和必需上下文，再调用一个或多个专业智能体。专业智能体只处理自己的职责，不直接修改业务状态。

### 9.2 结构化输出

画像、岗位匹配、任务计划、评分和风险建议均使用固定 JSON Schema 输出。业务服务验证通过后再保存，避免直接解析自然语言。

### 9.3 人工确认点

以下内容必须经过用户确认：

- 从简历抽取的学生档案。
- AI 推荐的目标岗位和四周计划。
- 简历中的事实性修改。
- 投递和面试结果。
- 辅导员风险确认与干预动作。

### 9.4 知识库引用

涉及就业政策、学校流程或岗位要求时显示来源名称、发布日期和原文片段。检索不到可靠材料时明确说明，不编造答案。

## 10. 异常与降级处理

- 模型不可用：保留用户输入和任务状态，提示稍后重试，不重复创建记录。
- 文件解析失败：允许手工填写或粘贴简历文本。
- 输出格式错误：自动重试一次，仍失败则保存草稿并提示人工处理。
- 知识检索无结果：提供通用建议并明确标注“未匹配校内知识库”。
- 岗位信息不完整：先列出缺失字段，不生成虚假企业或薪资信息。
- 风险规则误触发：辅导员可标记无效并填写原因，系统保留审计记录。
- 平台暂未开通：通过本地模拟数据和兼容模型完成端到端演示，接入后不改业务流程。

## 11. 隐私、安全与伦理

- 遵循最小必要原则收集数据，简历和求职记录仅对学生本人及授权辅导员可见。
- 展示、演示和训练数据必须脱敏，不将真实简历直接作为公开训练材料。
- 文件存储、数据传输和敏感字段采用适当的访问控制与加密措施。
- AI 生成内容标明为辅助建议，不替代学生决定或辅导员专业判断。
- 禁止伪造经历、证书、项目成果和面试结果。
- 提供数据更正、删除和授权撤回机制。

## 12. 首版范围

### 12.1 必须实现

1. 学生和辅导员双角色登录。
2. 简历上传、结构化档案抽取与人工确认。
3. 就业画像、目标岗位和四周计划。
4. 单个岗位的匹配分析。
5. 针对岗位的简历优化。
6. 文本模拟面试与反馈。
7. 投递看板和状态更新。
8. 每周求职复盘。
9. 辅导员班级看板、风险依据和帮扶任务。
10. 至少一条 SF-FastGPT 多智能体工作流演示。

### 12.2 暂不实现

- 自动爬取招聘网站或代替学生自动投递。
- 就业成功率预测和学生排名。
- 视频面试中的表情、外貌或声纹分析。
- 复杂校级组织、收费、即时通信和移动客户端。
- 大规模模型微调；首版优先使用知识库、提示词和工作流优化。

## 13. 测试与评价方案

### 13.1 功能测试

- 覆盖学生建档到投递复盘的主流程。
- 覆盖辅导员发现风险、布置任务和收到反馈的闭环。
- 覆盖模型超时、文件失败、格式错误和权限越界。

### 13.2 Agent 效果测试

建立一组脱敏标准样例，评价以下指标：

- 档案抽取字段准确率。
- 岗位匹配证据引用准确率。
- 简历建议的事实一致性和岗位相关性。
- 面试问题与目标岗位的相关性。
- 计划任务的可执行性。
- 风险规则触发准确率。

每项采用自动校验和人工评分结合，不仅展示主观案例。

### 13.3 可用性测试

邀请少量毕业生和辅导员完成指定任务，记录任务完成率、耗时、理解偏差和修改意见。首轮目标是主流程无阻塞，关键 AI 结论均可理解、可修改、可追溯。

## 14. 五分钟比赛演示脚本

### 0:00-0:30 痛点与产品定位

说明毕业生求职信息分散、计划难执行，辅导员难以及时发现停滞学生。展示学生端和辅导员端双端首页。

### 0:30-1:30 建档与规划

上传一份脱敏简历，AI 抽取档案；学生确认后生成能力画像、主目标岗位和四周任务。

### 1:30-2:30 岗位与简历

选择一个真实结构的岗位描述，展示匹配证据、能力差距和简历针对性修改，强调不虚构经历。

### 2:30-3:20 模拟面试与投递

完成一个岗位问题和一次动态追问，展示评分依据；随后将岗位加入投递看板并记录结果。

### 3:20-4:20 辅导员干预

切换辅导员端，展示某学生因“连续 14 天无投递”被标记为需干预，查看事实依据并布置岗位筛选任务。

### 4:20-5:00 闭环与技术亮点

切回学生端完成任务，辅导员看板同步更新。最后展示 SF-FastGPT 中主智能体调用专业智能体的工作流和平台分工。

演示准备两条路径：在线模型正常时走真实流程；模型异常时使用同一输入对应的预生成脱敏结果，确保展示不中断，并明确说明降级状态。

## 15. 创新点

1. 从一次性咨询升级为持续求职事务闭环，AI 建议能够转化为任务并被跟踪。
2. 学生端与辅导员端共享同一求职事件链，实现个体服务与班级管理联动。
3. 多智能体围绕统一档案和目标岗位协同，输出边界清晰且便于测试。
4. 风险识别采用规则事实、大模型解释和人工确认结合，兼顾效率与责任边界。
5. 岗位匹配、简历修改和面试评价均展示证据，降低大模型幻觉影响。

## 16. 实施阶段

### 第一阶段：原型与数据准备

- 完成双端交互原型和核心数据结构。
- 准备脱敏学生、岗位、简历和政策演示数据。
- 定义所有 Agent 的输入输出 Schema 和评价样例。

### 第二阶段：学生求职闭环

- 实现建档、画像、规划、岗位匹配、简历优化、面试和投递看板。
- 使用兼容模型接口完成端到端流程。

### 第三阶段：辅导闭环

- 实现班级看板、规则预警、学生详情和帮扶任务。
- 打通学生反馈与辅导员确认。

### 第四阶段：赛事平台接入

- 在取得账号和培训后，将 Agent 工作流迁移至 SF-FastGPT。
- 接入超星 AI 能力中心的可用模型能力。
- 从百川云璟导入合规数据并补充测试集。

### 第五阶段：测试与参赛材料

- 完成功能、效果、权限、异常和演示稳定性测试。
- 准备项目概要、详细方案、答辩 PPT 和 3 至 5 分钟演示视频。

## 17. 参赛交付物建议

- 项目概要介绍：一页说明用户、痛点、闭环和效果。
- 项目简介 PPT：问题、方案、架构、演示、创新、验证和规划。
- 项目详细方案：以本文档为基础补充界面截图和测试结果。
- 演示视频：按五分钟脚本录制，重点展示双端状态同步。
- 补充材料：Agent 工作流图、数据字典、提示词版本、测试集和评测报告。

## 18. 验收标准

项目首版满足以下条件即可进入参赛打磨：

1. 学生端主流程可以用一组脱敏数据完整跑通。
2. 至少三个专业智能体由主智能体按上下文调度，而非分别展示静态页面。
3. 所有写入学生档案和业务状态的 AI 结果均经过结构校验或人工确认。
4. 辅导员能够看到风险事实并完成一次有回执的干预。
5. 模型或文件处理失败时，系统不会丢失记录或阻塞整个演示。
6. 项目能够说明三项赛事工具分别解决什么问题，并现场展示 SF-FastGPT 工作流。
7. 使用至少一组标准样例给出可复现的 Agent 效果评价结果。
